# HumanGPT

**A human-in-the-loop, OpenAI-compatible mock endpoint for QA/testing.**

No AI generates responses. Every request to the OpenAI-compatible HTTP API is
persisted and parked in a queue; a human operator answers it through a web UI;
the human's typed reply is returned to the caller in the exact OpenAI response
shape. This lets a team exercise their OpenAI SDK integrations, prompts, tools,
streaming code, and vision flows with **full human control** over the "model's"
output — including deterministic canned answers for regression tests.

Flow:

1. An SDK client calls the endpoint with `base_url` pointed at this server.
2. The server validates the body (OpenAI-shaped errors otherwise), persists the
   full request, assigns a request ID, and **parks** the client's HTTP request.
3. The operator sees the pending request in the UI (full message chain, tool
   schemas, generation params, images rendered inline for vision requests).
4. The operator types the assistant reply — in **word-chunk** streaming mode
   each completed word is streamed to the client the moment a space/newline is
   typed and then locked (can't be edited), exactly like watching an LLM
   generate tokens. **Shift+Enter** finishes the response. Optionally the reply
   can be flagged as a `tool_call` (name + JSON arguments).
5. The server releases the parked client request with the human's answer wrapped
   in the correct OpenAI envelope (SSE when `stream:true`).
6. Every interaction is logged with the full request/response/operator-audit
   trail in SQLite.

## Supported API surface

| Route | Notes |
|---|---|
| `GET /v1/models` | configurable list from `MODELS_CONFIG`; OpenAI `list` envelope |
| `POST /v1/chat/completions` | `model`, `messages` (system/user/assistant/tool/developer), `max_tokens`, `temperature`, `top_p`, `seed`, `stop`, `presence_penalty`, `frequency_penalty`, `logprobs`/`top_logprobs` (echoed, not computed), `response_format`, `metadata`, `user`, `tools`, `tool_choice`, `stream`, `stream_options.include_usage`, `n`; vision `content` parts (`text`/`image_url`, http(s) **and** `data:` URIs) |
| `POST /v1/responses` | `model`, `input` (string or item array incl. `message` and `input_image` vision items), `instructions`, `tools`, `tool_choice`, `max_output_tokens`, `temperature`, `top_p`, `seed`, `stream`, `metadata`, `store`, `previous_response_id`, `include` |

Unknown/extra JSON fields are **tolerated** (like the real API); structurally
invalid bodies are rejected with OpenAI-style errors:

```json
{"error": {"message": "…", "type": "invalid_request_error", "param": null, "code": "invalid_request"}}
```

status codes: `400` malformed body / missing fields, `401` bad API key,
`404` unknown request, `409` answer race, `503` interrupted/discarded,
`504` timeout.

### Non-streaming envelopes

Chat completions return `id`, `object=chat.completion`, `created`, `model`,
`system_fingerprint`, `usage`, and `choices[0]` with
`finish_reason` (`stop`, or `tool_calls` when the operator flags it) and
`message.role=assistant`. Responses API returns the `response` envelope with
`output` items (`message` with `output_text` parts, or `function_call`).

### Usage heuristics (documented approximation)

OpenAI tokenization is opaque, so `usage` is a documented approximation:

- **prompt tokens**: `len(text.encode("utf-8")) / 4` per message (UTF-8 bytes ÷
  4, min 1), always ≥ 1; tool/function definitions count via their compact JSON
  encoding. Base64 `data:` images count as 765 tokens; http(s) image URLs as 85.
- **completion tokens**: same bytes÷4 rule on the human's answer.
- **total**: prompt + completion.

Deterministic given the same request+answer, so tests can assert on it.

### Streaming spec

`stream:true` requests are still queued and answered by the human. Two delivery
modes, selectable globally in the **Settings** page (not per request):

- **`word-chunk`** (default, live): as the operator types in the answer box,
  each completed word (followed by a space/newline) is **streamed to the parked
  client immediately** and then **locked** — the already-sent text can't be
  edited, exactly like watching an LLM generate. `Shift+Enter` (or the
  "Finish response" button) sends the terminal chunk. `MOCK_STREAM_CHUNK_DELAY_MS`
  throttles the per-word pace.
  - Typing is **exact**: a separator is consumed exactly once (typing
    `1 2 3 4 5` requires one space per word, and is streamed as deltas
    `["1"," 2"," 3"," 4"," 5"]`), and the final answer has **no trailing
    space** (a trailing separator is trimmed at finish). The pure lock logic
    lives in `ui/src/wordlock.js` and is unit-tested (`npm test`).
  - The endpoint **reconciles** the stream: if the caller streamed only part
    of the answer, the remaining suffix is emitted before the terminal frames,
    so the client's accumulated text always equals the envelope.
- **`once`**: the operator types freely, clicks **Submit**, and the whole
  answer is delivered as a single content delta.

**Chat completions SSE** — `data: {json}\n\n` framing; live words appear as
`delta.content` chunks as they're typed, then on finish:

1. final chunk with `finish_reason`
2. usage chunk when `stream_options.include_usage`
3. `data: [DONE]`

Tool-call answers stream the `delta.tool_calls` sequence (id/name first, then
argument fragments) with `finish_reason="tool_calls"` + `[DONE]`.

**Responses API SSE** — `event: <type>\ndata: {json}\n\n` framing, exact order:

```
response.created → response.in_progress → response.output_item.added →
response.content_part.added → response.output_text.delta (per typed word) →
response.output_text.done → response.content_part.done →
response.output_item.done → response.completed
```

Consumed without errors by `openai-python` — proven by the SDK integration
tests (`tests/test_sdk_integration.py`).

## Operator UI

The operator UI is a **React + Tailwind single-page app** (built into
`humangpt/web/static/dist`, served by the FastAPI app; no build step needed to
run — the committed bundle is served directly). It talks to JSON endpoints
under `/api/*` and is organised as tabs in a top bar with a live pending-count
badge:

- **Queue** (`/`): a true **master–detail layout** — the pending queue is a
  list on the left, and the selected request's detail fills the main pane on
  the right. Selecting a queue item loads it **in place** — there is no page
  switching between the queue and the request being answered. Each queued item
  shows status badge, model, snippet, tool tags, vision/SSE flags, claim and
  age. Live updates stream over SSE (`/events`).
- **Request detail**: message chain, vision images rendered inline, tool
  schemas, generation parameters, raw-JSON toggle, and the answer box. The
  word-chunk answer box shows the locked (already-streamed) text above the
  editable draft tail, and **Shift+Enter** finishes. An in-progress draft
  auto-saves per request (localStorage) so switching messages loses nothing.
- **History** (`/history`): terminal-state requests with full transcript
  (request JSON, human response envelope, finish_reason, usage, answered-by/at)
  for QA auditing.
- **Templates** (`/templates`): create / edit / delete canned responses and
  copy a body. Insertable (unlocked) into the answer box.
- **Settings** (`/settings`): **Copy API URL** button, stream-mode default +
  chunk delay, and the **model catalog editor** — add new model ids and set
  per-model `description` / `pricing` (merged with `models.json`, served by
  `/v1/models`).

To rebuild the SPA after touching `ui/`:

```bash
cd ui && npm install && npm run build   # writes humangpt/web/static/dist/
cd ui && npm test                        # unit-test the word-lock logic
```

The committed build is served directly, so **no Node toolchain is needed just to
run** HumanGPT.

Readability: clean system font stack, 17px base, dark theme, generous spacing.

### Concurrency rules

- **Soft claim**: opening a pending request stamps `claimed_by`/`claimed_at`
  (badge shown); anyone may steal it with the claim button; no locks.
- **Double-submit race**: the atomic `pending → answered/streamed` transition
  wins. The second submit gets `409 request_not_pending` and is dropped, so
  exactly one response row exists per answer and the parked coroutine wakes
  exactly once.

## Data model & persistence

SQLite (configurable path). Tables:

- `requests` — id, endpoint, model, full raw JSON `body`, parsed `summary`,
  `state`, `created_at`, `answered_at`, `answered_by`, `claimed_by/at`,
  `interrupted_at`, `stream_mode` default, `timeout_at`.
- `responses` — linked to request, full response JSON, `finish_reason`,
  `is_tool_call`, `tool_name`, `tool_arguments`, `stream_mode`, `created_at`.
- `templates` — name, body, timestamps.
- `models_meta` — `model_id`, `description`, `pricing` (JSON string) —
  user-editable model details from the Settings page, **merged** with
  `models.json` (file = identity; DB overlays description/pricing and can add
  brand-new model ids).
- `settings` — key/value store for the Settings panel (stream-mode default,
  chunk delay).

### Restart behaviour (documented)

Parked HTTP requests live **in this process** (see below), so:

- **Graceful shutdown** (SIGINT/SIGTERM): a signal hook installed by the
  `humangpt` entry point interrupts parked requests *before* uvicorn waits for
  open connections to close (uvicorn's own connection-wait would otherwise
  deadlock on parked, long-lived client connections). Every still-pending
  request is transitioned `pending → interrupted` and released with a `503
  api_connection_error` (code `server_interrupted`), so SDK clients raise a
  clean exception instead of hanging.
- **Crash / `kill -9`**: the row stays `pending` but is orphaned. On next
  boot the **startup sweep** transitions any `pending` row to `interrupted`
  (with `interrupted_at`), keeping the state machine honest.

### Single-worker requirement

The queue parking is an in-process asyncio table (`humangpt/parking.py` →
`ParkingLot` protocol). Multiple uvicorn workers would each hold their own
table and strand clients across processes, so the entry point **forces
`workers=1`** (and `WEB_CONCURRENCY>1` is rejected at boot). The `ParkingLot`
interface is the documented seam for a future DB/pub-sub-backed parking
implementation if multi-worker support is ever needed.

## Configuration

All settings are env vars / `.env` (see `.env.example`). `0`/empty disables the
feature where sensible.

| Variable | Default | Meaning |
|---|---|---|
| `HOST` | `127.0.0.1` | bind address |
| `PORT` | `8000` | bind port |
| `DB_PATH` | `data/humangpt.db` | SQLite file (directories auto-created) |
| `OPENAI_API_KEY` | *(unset)* | **any** Bearer key accepted (easy testing). When set, incoming `/v1/*` calls MUST send exactly this key or get `401 invalid_api_key`. The UI is never key-protected. |
| `MOCK_REQUEST_TIMEOUT_S` | `600` | how long a request may sit pending before the parked client is released with `504 request_timeout`. `0` disables. |
| `MOCK_STREAM_CHUNK_DELAY_MS` | `0` | inter-word delay in live `word-chunk` streaming (0 = deliver as fast as the operator types). |
| `MOCK_STREAM_MODE` | `word-chunk` | default stream mode (`word-chunk` / `once`); overridable in the Settings page. |
| `MODELS_CONFIG` | `models.json` | path to the JSON model list (`{"models": [{id, created, owned_by}]}`). |
| `CORS_ORIGINS` | `*` | comma-separated allowed origins (UI is same-origin; only needed for cross-origin JS). |
| `UI_SSE_KEEPALIVE_S` | `25` | SSE keepalive interval for `/events`. |
| `UI_POLL_INTERVAL_S` | `10` | *(reserved)* JS fallback poll interval. |

### Security note

HumanGPT binds to `127.0.0.1` by default, has no authN/Z beyond the optional
static API key, and intentionally never fetches images server-side (the browser
loads them) so there is no SSRF surface. It is a QA testing utility — do **not**
expose it publicly or on a shared network without a reverse proxy + proper auth
in front of it. (See the AI-generated disclaimer at the top of this README.)

## Project layout & how to add a new `/v1` endpoint later

```
humangpt/
├── app.py            # composition root: app factory, lifespan, API-key middleware
├── config.py         # .env/env-driven settings (no pydantic-settings dep)
├── container.py      # AppState wiring (settings, db, queue, models, hub)
├── core.py           # PURE logic — state machine, word-chunking, token heuristics,
│                     #   envelope builders, LiveBuffer (unit-tested in isolation)
├── db.py             # SQLite layer (stdlib sqlite3, thin typed wrapper)
├── parking.py        # ParkingLot protocol + asyncio impl (FIFO deltas+result) + QueueService + timeout sweep
├── hub.py            # tiny in-process pub/sub for the operator SPA's live updates
├── tokens.py         # usage heuristics (documented approximation)
├── summary.py        # operator-friendly parsed summary stored per request
├── models.py         # Pydantic v2 request/response models (the API contract)
├── respond.py        # wraps a human answer in the exact envelope for an endpoint
├── sse.py            # chat-completions + responses SSE frame encoders
├── live_stream.py    # live-typing streaming endpoint assembly (word-chunk deltas)
├── endpoint_utils.py # shared endpoint helpers (parse, park, release, serve)
├── endpoints/        # ONE module per /v1 resource group
│   ├── models.py     #   GET /v1/models
│   ├── chat.py       #   POST /v1/chat/completions
│   └── responses.py  #   POST /v1/responses
├── api/              # JSON operator API consumed by the React SPA
│   └── routes.py     #   /api/* — queue, detail, actions, templates, settings
├── routers.py        # /v1 APIRouter registry (include new groups here)
└── web/              # serves the built React SPA
    ├── routes.py     #   SPA shell + /events SSE live updates
    └── static/
        └── dist/     #   committed Vite build (index.html + assets/)

ui/                   # React + Tailwind SPA source (dev only; the committed
                      # build in humangpt/web/static/dist is what's served)
```

**To add, e.g., `/v1/embeddings`:**

1. Create `humangpt/endpoints/embeddings.py`:

   ```python
   from fastapi import APIRouter, Depends
   from starlette.requests import Request
   from ..container import AppState
   from ..deps import get_state

   router = APIRouter(tags=["embeddings"])

   @router.post("/embeddings")
   async def embeddings(request: Request, state: AppState = Depends(get_state)):
       # parse request, create a pending row (endpoint="/v1/embeddings"),
       # await state.queue.park(...), serve the human answer — copy the
       # pattern from humangpt/endpoints/chat.py
       ...
   ```

2. Register it in `humangpt/routers.py`:

   ```python
   from .endpoints import chat, embeddings, models, responses
   v1_router.include_router(embeddings.router)
   ```

3. Add the operator-answer builder in `humangpt/respond.py`
   (`build_embeddings_response(...)`) and a summary in `humangpt/summary.py`.

No other file changes are needed — the queue, parking, UI, timeout, restart and
audit machinery are all endpoint-agnostic.
